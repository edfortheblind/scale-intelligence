HTTP Headers in REST-Based Web Services
View with Navigation Tools

The following table describes the common use of HTTP headers by REST-Based Web Services in the application.  A specific service may override this default behavior, which will be described in the service's specific help topic.

For general information about HTTP Headers, consult the corresponding section of the HTTP specification.

 

Header Description
Accept

Communicates to the application the acceptable media types to include in response.  Acceptable values include application/json, application/xml, or a resource specific media type.  See each individual service's help topic for specifics.

If a suitable media type cannot be determined, an error response with status code 406 (Not Acceptable) will result.
Accept-Encoding

Communicates to the application the acceptable encodings that will be applied to the corresponding response entity.  See Compression in REST-Based Web Services for an example of where this header is used.

Note the following:

  • Currently supported encodings: gzip, deflate
  • The first supported encoding will always be honored across all services.
  • Parameters such as "q" values are ignored.
  • The special "identity" and "*" encodings are not supported.
  • If an Accept-Encoding is specified but no supported encodings are listed, an error response with status code of 406 (Not Acceptable) will result.
Accept-Language Communicates to the application the acceptable languages that should be used for localizable data on responses.  The application will use the first supported language in the list, and if none of the languages are supported or the Accept-Language is empty, the server's default language will be used.
Authorization

A Oauth 2.0 Bearer Token is set in the Authorization header of every Inline Action HTTP Request. For example:

"Authorization: Bearer <AbCdEf123456>"

The string "AbCdEf123456" in the example above is the bearer authorization token.

If using bearer tokens, verify that the request is coming from the intended sender domain. If the token doesn't verify, the service should respond to the request with an HTTP response code 401 (Unauthorized)

See Authentication in REST-Based Web Services for more information.
Environment

If no environment are configured this value should be passed as Defaultaabf6698-37ae-45ee.

If environments are configured this value should be the name of environment to which web service to be called. Environment name should match subdomain of hostname.
Cache-Control May be specified by The application to suggest how the client should cache a returned entity.  For example, if performing a GET on a resource that represents live, frequently changing data, a Cache-Control of no-cache may be returned.
Content-Encoding

Describes the encoding that was applied to the included entity.  See Compression in REST-Based Web Services for an example of where this header is used.

Note the following:

  • Currently supported encodings: gzip, deflate
  • The encodings applied by SCALE to a response entity are governed by the Accept-Encoding header on the request.
  • During a POST or PUT, a Content-Encoding may be specified on the request, which will force the application to decode the request entity before processing.  If the Content-Encoding contains an unsupported encoding value, an error response with status code of 415 (Unsupported Media Type) will result.
Content-Type

Describes the media type of the entity attached to both requests and responses.

Requests must include this header for POSTs and PUTs.  If the specific media type of the attached entity is not know, then application/json or application/xml must be supplied.  If the media type is not recognized, an error response with status code of 415 (Unsupported Media Type) will result.

The application will respond with the specific media type of a resource when available.  See each individual service's help topic for specifics.  Each media type ends with either json or xml to describe the serialization format.
MachineName

Indicates the client's machine name. In case of a terminal services user, it represents the machine from which the terminal services session was opened. It is the responsibility of the web service consumer to appropriately set this header.
Warehouse

Indicates the warehouse for which web service to be called
