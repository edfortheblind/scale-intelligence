Standard Responses from REST-Based Web Services

The following table describes standard Manhattan SCALE response status codes and their typical meaning.  For additional information, including exceptions to the following, please see each individual service's help topic.

There are also standard responses returned by the hosting technologies used by the application, such as Microsoft IIS, ASP.NET, etc.  If a particular response does not follow what is documented here or in the help for the service, see the corresponding section of the HTTP specification for more general information about HTTP status codes.

 

Status Code Description
200 OK.  The request has succeeded.
400

Bad Request.  The request could not be understood by the application or was invalid and should not be resubmitted without modification.  This could occur under the following circumstances:

  • Missing or invalid header information, such as Session or a header specifically required by the service.
  • The data specified in the query string or entity is invalid (wrong structure, data type, etc.).
401 Unauthorized.  The request could not be authenticated.  See Authentication in REST-Based Web Services for more information.  Note that the entity that accompanies this response is typically generated by IIS.
403

Forbidden.  The request was understood and accepted by the application but something unrelated prevented its processing.  To overcome errors of this type, some factor outside the scope of the request must be changed before resubmitting the original request.

The main difference between Forbidden and Bad Request is that Forbidden typically cannot be handled by the current consumer.  For example, if attempting to close a shipping container that is in an invalid status, the user requesting the close will have to perform a completely different action (if possible) in order to get the container to a valid state.
404

Not Found.  The resource at the given URI does not exist.

Note that this could mean that the URI specifies the wrong web site, which is not handled by the application and may return an entity that does not conform to the below structure.
406

Not Acceptable.  Occurs when either the Accept or Accept-Encoding headers are specified but do not contain a supported media type/encoding.

The entity accompanying the response will list the supported media types/encodings, and will be formatted using "application/json" if an acceptable media type cannot be determined.
415

Unsupported Media Type.  Occurs when either the Content-Type or Content-Encoding headers of a request describe a media type/encoding that is not supported.

The entity accompanying the response will list the supported media types/encodings.
500

Internal Server Error.  Returned under the following circumstances:

  • A valid request was received but external factors prevented the application from processing the request.  An example of this includes concurrency errors with other users/processes in the application. 
  • The application encountered an unexpected system or environmental error that prevented it from processing the request.

The application makes every attempt to record additional information to either the Audit or Event Log.

Note that this could be returned by the server hosting the web service before the application has a chance to process the request.  In that situation, the application may not be able to make record of the error, and the entity may not conform to the below structure.

 

All generated error responses (those with status codes 4xx or 5xx) will be accompanied by an entity that adheres to one of the following media types:

application/vnd.manh.ils.error+json

application/vnd.manh.ils.error+xml

The preferred media type of the Accept header will be used to determine the serialization format of the error entity.

The below tables describes the fields of this resource:

Field Description
ErrorCode A string that uniquely identifies the error.  May be used by the consumer to react to specific error situations.  For example, a consumer may catch a particular error, ask the end user for confirmation or additional information, and then re-issue the request given the new information.  Such situations may be documented in the help of each service.
ErrorType

An enumeration that describes the type of error.  May be used by the consumer to react to general error situations.  For example, a consumer may catch all errors of a particular type in order to highlight a specific field.  Each service should document the known returned ErrorTypes, which typically correspond to the fields listed on the request.
Message

The message describing the error, localized in the culture specified in the Session header.
AdditionalErrors

An optionally populated collection of error information.  See each web service's help topic to determine if and when multiple errors are returned.
