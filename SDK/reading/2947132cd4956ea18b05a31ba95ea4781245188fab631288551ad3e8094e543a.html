The SCALE metadata driven web screens are rendered as web pages using HTML and JavaScript. They are built with the standard VisualStudio ASP.NET MVC 5 Web Application project using the Razor View Engine. This enforces a separation of the Model, View, and Controller (MVC) portions of the project. There are many advantages to this architecture including but not limited to managing complexity, better support for test driven development (TDD), and better web routing. There is a lot of online documentation regarding MVC that can be referenced, but here is a good starting site: http://www.asp.net/mvc/tutorials/older-versions/overview/asp-net-mvc-overview. The following table gives details on some basic ASP.NET MVC concepts and terminology.

Concept Description
Model Portion of the system that implements the logic for the application’s data domain. Model objects generally retrieve and store model state in a database.
View Portion of the system that displays the application’s user interface (UI).
Controller Portion of the system that handles user interaction, works with the model, and ultimately selects a view to render that displays the UI.
Razor View Engine One of the default view engines in ASP.NET MVC 5 that allows for the use of embedded C# in the view – represented by the "cshtml" file extension (http://channel9.msdn.com/coding4fun/articles/Developer-Review-Four-ASPNET-MVC-View-Engines).
Bundling Combining resources such as JavaScript into a single file to reduce HTTP requests and improve performance (http://www.asp.net/mvc/tutorials/mvc-4/bundling-and-minification).
Minification The practice of removing unnecessary characters from code to reduce its size and improve load times.
Routing Allows URLs that do not map to specific files and are therefore more "readable" to users. Routing in ASP.NET MVC 5 is done in the RouteConfig.cs file which is under the App_Start folder.
JQuery Fast, small, and feature-rich JavaScript library (http://jquery.com/).


Each metadata screen is built with a series of different metadata records called screen parts, groups, group columns, controls, and control events. This concept is illustrated below:

 

 Metadata Structure

Metadata in SCALE resides in the database as standard SQL Server tables. When a URL is requested and properly routed, SCALE reads the metadata for the screen on the server and then renders the corresponding HTML on the client browser. This server side logic simply iterates through the metadata table structure, rendering the HTML for the screen parts, groups, controls, etc. The below illustrates the SCALE metadata structure:

Metadata Term SQL Server Table Name Description
Form FORM Represents a single screen at the highest level. All screens in the system (desktop, RF, metadata, etc.) have a Form record.
Security SECURITY_CHECKPOINT The security checkpoints defined for the form. Some checkpoints are pre-defined (run, edit, display, etc.) and some can be form specific.
Screen MAIN_UI_SCREEN A single screen implementation of a Form. A single Form can have a max of two Screen implementations - the "base" implementation and a single "custom" implementation. Only one of these can have Active = Y at a time. The "base" screen is defined as any Screen record that has system_created = Y. The base SCALE installer will only overwrite Screen implementations with system_created = Y.
Screen Part SCREEN_PART

A screen part is a logical grouping on a screen. Currently all screen parts are rendered as divs. An example of a screen part would be the Search Pane on an Insight screen. See the Getting Started: Metadata Web Pages topic for an illustration of screen parts. Also see How to: Create Screen Parts and Supported Screen Parts.
Screen Group SCREEN_GROUP

A screen group is a logical grouping inside a screen part. Some examples of screen groups would be tab controls and accordion controls. Please reference the How to: Create Screen Groups and Supported Screen Groups topics for more information.
Screen Group Column SCREEN_GROUP_COLUMN

A screen group column allows for bootstrap columns to be defined inside of a screen group. Please reference the How to: Create Screen Group Columns topic for more information.
Screen Control SCREEN_CONTROL

A screen control represents a single control on the page inside of a screen group. Some examples of screen controls would be text editor, numeric editor, grid, etc. Please reference the How to: Create Screen Controls and Supported Screen Controls topics for more information.
Screen Control Attributes SCREEN_CONTROL_ATTRIBUTES

A screen control attribute allows for either 1) setting supported properties on a control, or 2) tying an HTML attribute tag to a control for use in Javascript/JQuery. Please reference the How to: Create Screen Control Attributes and Supported Control Properties topics for more information.
Screen Control Grid Columns SCREEN_CONTROL_GRID_COLUMNS

A screen control grid column record applies only to grids, and it defines the columns inside the grid. Please reference the How to: Create Screen Control Grid Columns topic for more information.
Screen Control Event SCREEN_CONTROL_EVENT

A screen control event record binds an event to a control (such as onclick, onfocus, etc.). Please reference the How to: Create Screen Control Events and Supported Screen Control Events topics for more information.
Screen Control Event Parameters SCREEN_CONTROL_EVENT_PARAMETERS

A screen control event parameter record defines a parameter that should be passed to an event. Please reference the How to: Create Screen Control Event Parameters and Screen Control Event Parameter Naming Conventions topics for more information.
