
        
        <h1 data-source-node="n56"><a name="kanchor2027" data-source-node="n57"></a>Backing Up an SQL Server Database</h1>
        <p data-source-node="n58">The following procedure is recommended as the minimum strategy/plan 
 for backing up system SQL Server Databases. This plan allows for recovery 
 to exact points in time of the database server, assuming all necessary 
 files are not corrupted. Basically, the plan outlines the parameters of 
 how you want to back up your database.</p>
        <p data-source-node="n59"> </p>
        <p data-source-node="n60"> </p>
        <h4 data-source-node="n61">Procedures...</h4>
        <p data-source-node="n62"> </p>
        <p data-source-node="n63">Access your database server.</p>
        <ol class="ol_1" data-source-node="n64">
            <li value="1" data-source-node="n65">Open the SQL 
 Server Enterprise Manager, which is the central management tool 
 for SQL Server 2000. :<br data-source-node="n66"> </li>
            <li value="2" data-source-node="n67">If needed, expand 
 the tree on the left pane. To configure your database backup plan, 
 expand the Management folder and click on the Database Maintenance Plan. 
 <br data-source-node="n68"> </li>
            <li value="3" data-source-node="n69">Right-click the 
 pane on the right and select the option to create a new maintenance plan. 
 The system will display a wizard to walk you through this process. Select 
 Next when ready. :<br data-source-node="n70"> </li>
            <li value="4" data-source-node="n71">Select the system 
 database as the database involved in the backup plan.  Select 
 Next when finished. :<br data-source-node="n72"> </li>
            <li value="5" data-source-node="n73">Select the Perform 
 Data Reorganizations checkbox. By default, these are scheduled 
 for once a week, which should be acceptable. Reorganizing the data is 
 similar to de-fragmenting your hard drive on your PC, except at a database 
 level. This helps to maintain performance on your server. Press Next when 
 finished. :<br data-source-node="n74"> </li>
            <li value="6" data-source-node="n75">Select the Check 
 Database Integrity checkbox. This is done to ensure that no corruption 
 has occurred during usage. Checking for this once a week is acceptable. 
 Press Next when finished. :<br data-source-node="n76"> </li>
            <li value="7" data-source-node="n77">Next, you will 
 define the backups for the database. Recovering data without backups 
 is almost impossible. You should configure a daily backup of the database. 
 To change the schedule from the default weekly one, click the Change button 
 and specify a time each day where there is minimal processing occurring. 
 Remember that you will want to schedule the job to run before any tape 
 backups occur on the machine. This ensures that the backup is archived 
 to tape to prevent loss from a later disk failure. This can normally be 
 scheduled for about one hour before any tape backup procedures start. 
 This delay should provide sufficient time for the backup to be completely 
 written. Press Next when finished. :<br data-source-node="n78"> </li>
            <li value="8" data-source-node="n79">Specify the location 
 where the backups should be written in the next screen. It is recommended 
 that you turn on the option to save a limited number of days to this directory. 
 Four days is a typical time span. Backup files can become quite large 
 over time, so this will help minimize disk space constraint issues. Press 
 Next when finished. :<br data-source-node="n80"> </li>
            <li value="9" data-source-node="n81">Next, you need 
 to configure transaction log backups. The transaction log stores 
 every change made to the database and is the other critical piece of the 
 recovery strategy. It is recommended to take a transaction log backup 
 a minimum of every two hours throughout the day. The transaction log backups 
 will be needed for recovery until the regular daily backup is performed. 
 Without these log backups, data can only be recovered to the last successful 
 daily backup. You can save these to the same directory as the daily backup, 
 and keep two days worth of logs. Press OK when finished. : <br data-source-node="n82"> </li>
            <li value="10" data-source-node="n83">Finally, set 
 up the maintenance plan to write output from the processes to text files 
 in a directory. This allows you to review the schedule jobs and 
 how they are running. It is recommended that you keep about the last two 
 weeks worth of logs to help troubleshoot any issues that could arise. 
 You do not need to keep any history in database tables or a remote server, 
 unless desired. Press Next when finished. :<br data-source-node="n84"> </li>
            <li value="11" data-source-node="n85">Upon completion 
 of the wizard, you will have defined a database backup plan that 
 will allow you to recovery from most disasters. Loss of backup files can 
 result in data loss, so they should be protected as much as possible. 
  It is recommended 
 that the files be stored on disks configured in a RAID architecture for 
 redundancy and routinely archived to tape or other long term storage media. Also, the directory used to store the backups should be located on 
 a separate physical drive than the database. Different drive letters does 
 not necessary mean different physical drives, so be sure to verify that 
 the drives are different. It is also highly recommended that tapes be 
 stored at a different physical location than the servers or in a fireproof 
 safe approved for tape storage. This will help prevent data loss due to 
 a natural disaster such as a fire.</li>
        </ol>
