        <h4 data-source-node="n65">Summary...</h4>
        <p data-source-node="n66">Cycle counting is the physical verification that inventory actually 
 present in a location matches what the system believes is in the location. 
 This helps you keep track of exactly how much inventory is present in 
 your warehouse. There are two ways you can trigger cycle counts: by manually 
 creating cycle count plans (called "plan-based"), or by having 
 the system create cycle count work instructions automatically when a location 
 is due for a cycle count (called "non-plan based" or "activity-driven").</p>
        <p data-source-node="n67"> </p>

        <p data-source-node="n83"> </p>
        <p data-source-node="n84"> </p>
        <h4 data-source-node="n85">Plan Based Cycle Counting...</h4>
        <p data-source-node="n86">One method you can use to trigger cycle count requests is by creating 
 cycle count plans. The settings on these plans determine which includes such information as which items/locations that the system will generate counts for. Once the counts are generated, users can confirm/reconcile plan-based cycle count 
 requests on an RF device, the Work Insight Screen, and on the Cycle Count Request Insight screen. You can also 
 have your cycle count plans generate requests automatically via scheduled 
 jobs.</p>
        <p data-source-node="n87"> </p>
        <p data-source-node="n88">SCALE features two types of plans: <i data-source-node="n89">master plans</i> and <i data-source-node="n90">quick plans.</i></p>
        <p data-source-node="n91"> </p>
        <p data-source-node="n92"><i data-source-node="n93">Master Plans...</i>
        </p>
        <p data-source-node="n94">Master plans feature cycle count requests that have been generated from pre-defined configuration records.  These cycle count "master" records contain information on how the system will create cycle count requests (via item and location selection filters), and 
 how those requests will be grouped. The system will generate cycle count requests according to this criteria. The master plan settings are stored in the Configurations Explorer and can be run multiple times. </p>
        <p data-source-node="n95"> </p>
        <p data-source-node="n96"> </p>
        <p data-source-node="n97"><i data-source-node="n98">Quick Plans...</i>
        </p>
        <p data-source-node="n99">Quick plans are generated dynamically by the user. The user can choose the parameters of the plan, such as the item/locations that will counted. Unlike master plans, quick plan settings are not stored as a configuration record for future use. Once the quick plan is created and run, the plan settings are not retained. </p>
        <p data-source-node="n100"> </p>
        <p data-source-node="n101"> </p>
        <p data-source-node="n102"> </p>
        <h4 data-source-node="n103">Non-Plan Based (Activity-Driven) Cycle Counting...</h4>
        <p data-source-node="n104">Non-plan based (activity-driven) cycle counting is the concept of triggering 
 the generation of a cycle count request after a warehouse activity is performed (such as 
 a pick). The triggering of these requests is tied to the location being 
 processed (e.g. a pick being done to a location). After the transaction 
 is executed, the location will be reviewed to see if a cycle count request 
 should be generated. These requests are created one at a time and dynamically (as opposed to the plan-based method where a number of requests can 
 be created at once). Activity-driven cycle counting is performed on an RF 
 device.</p>
        <p data-source-node="n105"> </p>
        <p data-source-node="n106">The Cycle Count Preference configuration has a setting that controls 
 whether these activity-driven requests should be executed immediately 
 or created as pending requests. If these requests are to be executed immediately, 
 the system will display a cycle count screen on the RF device. The user 
 then can execute the cycle count. However, if the system creates a pending 
 request, then the request will be executed at another time either through 
 RF or full-screen (depending on if the system flags are set up to create 
 work for activity-driven cycle counts). If you are not executing 
 work, this concept of immediate reconciliation does not apply; therefore, 
 the system will create all records as pending requests.</p>
        <p data-source-node="n107"> </p>
        <p data-source-node="n108"> </p>
        <p data-source-node="n109"> </p>
        <h4 data-source-node="n110">Counting Item Quantity vs. License Plates...</h4>
        <p data-source-node="n111">SCALE gives you the opportunity to configure the system to prompt the user to count the actual item quantity at a location, or to simply count the number of license plates that reside at the location. Furthermore, the user can have the ability to identify which license plates that they want to count, which is helpful if the first LP that the system wants them to count is stacked too high or far back in a location. Also, users can add new license plates "on the fly" when counting, which allows them to inform the system of previously unknown license plates.</p>
        <p data-source-node="n112"> </p>
        <h4 data-source-node="n113">Catch Weight in Cycle Count</h4>
        <p data-source-node="n114"> </p>
        <p data-source-node="n115">Cycle count processing supports catch weight for items configured as catch weight items. Depending on the count flow and count outcome, SCALE either captures catch weight input or updates catch weight by using average catch weight logic.</p>
        <p data-source-node="n116"> </p>
        <h5 data-source-node="n117">Standard Cycle Count</h5>
        <ul data-source-node="n118">
            <li data-source-node="n119">During the standard cycle count flow, SCALE does not prompt for catch weight during the regular count step.</li>
            <li data-source-node="n120">If the count is within tolerance, SCALE adjusts inventory automatically and updates catch weight by using average catch weight at the location multiplied by the quantity adjustment.</li>
            <li data-source-node="n121">If the count is outside tolerance, the request moves to pending review, and reconciliation updates both quantity and catch weight information.</li>
        </ul>
        <h5 data-source-node="n122">Blind Cycle Count</h5>
        <ul data-source-node="n123">
            <li data-source-node="n124">During blind cycle count, SCALE prompts for catch weight.</li>
            <li data-source-node="n125">For new inventory records created by the count, SCALE uses the catch weight entered during adjustment.</li>
            <li data-source-node="n126">For existing inventory records, SCALE uses average catch weight multiplied by the adjusted quantity.</li>
        </ul>
        <h5 data-source-node="n127">Other Counting Flows</h5>
        <p data-source-node="n128"> </p>
        <p data-source-node="n129"><b data-source-node="n130">Count License Plate</b> and <b data-source-node="n131">Group Count by Item/Company</b> continue to work as expected. If the count is off, SCALE routes processing through the standard count path.</p>
