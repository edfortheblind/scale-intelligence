
        
        <h1 data-source-node="n56"><a name="kanchor1192" data-source-node="n57"></a>Researching Printing Errors</h1>
        <p data-source-node="n58">Below are some troubleshooting tips that you can use to help diagnose 
 printing problems. If you still have questions, contact your Manhattan 
 consultant or call the support line.</p>

        <h4 data-source-node="n77"><a name="Audit" data-source-node="n78"></a>Audit Logs...</h4>
        <ul type="disc" class="ul_1" data-source-node="n79">
            <li data-source-node="n80">To perform additional 
 research or want to review technical information, access the Audit 
 Log Viewer Window and search for records, using criteria that meet your 
 user ID and the date/time when you initiated the request. Always check 
 the audit log first for errors from the following classes: PrintSupport, 
 WordPrintProcessing, and PrintProcessing. </li>
        </ul>
        <p data-source-node="n81"> </p>
        <p data-source-node="n82"> </p>
        <h4 data-source-node="n83"><a name="DocumentRout" data-source-node="n84"></a>Document Routing Records...</h4>
        <ul type="disc" class="ul_1" data-source-node="n85">
            <li data-source-node="n86">The data does 
 not match the criteria defined on any document routing record. 
 For the document to print, the printing criteria defined here must be 
 met. Review the document routing records and verify that at least one 
 record identifies the criteria values for the data.<br data-source-node="n87"><br data-source-node="n88"></li>
            <li data-source-node="n89">Note on Session Information and Document Routing:   
                The system gathers "session" information when the application starts up, and stores this information for the duration that the application is open (without ever re-retrieving it). When a user goes from one client workstation to another and uses a previously open or disconnected remote desktop (RDP) session (i.e., a "stolen" RDP session), the system will NOT need to re-retrieve the session information. Therefore, the document routing process uses the "original" client device name when determining where a document should be routed. In order to prevent this (and have the document routed to the new workstation), you need to log off the RDP session when finished with a work station; or, if you disconnect from one workstation and connect to the same session from another workstation, you need to close the application and re-open it.</li>
        </ul>
        <p data-source-node="n90"> </p>

        <h4 data-source-node="n92"><a name="DocumentServ" data-source-node="n93"></a>Printing Directory...</h4>
        <ul type="disc" class="ul_1" data-source-node="n94">
            <li class="li_1" data-source-node="n95">The system generates 
 data files to two directories when printing paperwork: 
 the "Print Data" and "Print Input" directories (which 
 are both sub-directories of the "Printing" directory on your 
 application server). The "Print Data" directory is used when 
 the system writes the data files it uses for printing. Note that these 
 files are 
 not deleted when there is an 
 error in printing. The "Print Input" directory is used when 
 the system writes the control files used when printing.<br data-source-node="n96"><br data-source-node="n97"></li>
            <li data-source-node="n98">Someone moved 
 the Printing Directory from its install location without changing the 
 location path in the Technical Values Window. When the system is 
 installed, the setup tools automatically load the Printing Directory in 
 the following location:        <i data-source-node="n99">\\WMAppServer\ILS\Printing</i>. 
 A record in the Technical Values Window identifies the physical location 
 of this folder on the server. If the physical location of the Printing 
 Directory is different than the location identified in this window, the 
 system cannot generate documents. </li>
        </ul>

        <h4 data-source-node="n102"><a name="Misc" data-source-node="n103"></a>Miscellaneous Hardware Errors...</h4>
        <ul type="disc" class="ul_1" data-source-node="n104">
            <li data-source-node="n105">Make sure the 
 batch submission service is started. If no control files are being 
 written to the "Print Input" directory, then this is most likely 
 the cause. To confirm that no control files are being written, the user 
 may have to stop the print engine on the application server. <br data-source-node="n106"> </li>
            <li data-source-node="n107">Is there a .<i data-source-node="n108">err</i> 
 file? If there is a ".err" file, then there will be a 
 corresponding audit log record matching that has details as to the problem. <br data-source-node="n109"><br data-source-node="n110"></li>
            <li data-source-node="n111">Make sure that 
 the console is always signed on with the same profile, since printers 
 are associated with a particular user profile. For example, printing may 
 work fine signed on as "Administrator"; but, if you sign on 
 to the console instead as "jdoe," the printing process will 
 potentially break.<br data-source-node="n112"> </li>
            <li data-source-node="n113">If there are 
 no control files being written, then the problem is not in the print engine. 
 Most likely, an audit log record will exist explaining why. Note that 
 the system places these control files in the "Print Input" directory. If an error occurs when you select to print or print preview, the system 
 usually displays an error message on the bottom of the screen. You can 
 rectify the error and try to print/print preview again.<br data-source-node="n114"> </li>
            <li type="disc" class="li_2" data-source-node="n115">If no message 
 is displayed onscreen or you need some direction in fixing the 
 error, see your Manhattan representative.<br data-source-node="n116"> </li>
            <li type="disc" class="li_2" data-source-node="n117">If a hard drive 
 error occurs during printing, the system will retry the disk operation 
 up to ten times, and generate an audit log record for each attempt.</li>
        </ul>

        <h4 data-source-node="n120"><a name="PrintDevice" data-source-node="n121"></a>Print Device...</h4>
        <ul type="disc" class="ul_1" data-source-node="n122">
            <li data-source-node="n123">Make sure that 
 the print device is identified correctly on the Print Device Window. 
 The printer name that you define on the print device window must exactly 
 match the printer's name that you defined via the Microsoft Windows Add 
 Printer action.</li>
        </ul>
        <p data-source-node="n124"> </p>

        <h4 data-source-node="n126"><a name="Progistics" data-source-node="n127"></a>Progistics Related...</h4>
        <ul type="disc" class="ul_1" data-source-node="n128">
            <li data-source-node="n129">If you are attempting 
 to print a Progistics generated label, did you receive the following 
 message: "No device is assigned to ****" (where **** is the 
 printer's share name)? If so, the printer's network name is different 
 than its share name and you have not communicated that difference to Progistics. 
 See Changing the Printer's Share Name for instructions. <br data-source-node="n130"> </li>
            <li data-source-node="n131">Is the label 
 stock must be compatible with the printer that you're using? Be 
 sure to verify that the stock and printer are compatible on the Print 
 Device Window. You need to do this if the document you are printing is 
 generated by Progistics.</li>
        </ul>

        <h4 data-source-node="n134"><a name="hanging" data-source-node="n135"></a>PrintProcessing "Hanging" (Non-Responsive)...</h4>
        <ul type="disc" class="ul_1" data-source-node="n136">
            <li data-source-node="n137">If, after you 
 or the system initiates a print job, and PrintProcessing seems 
 to be "hanging" (becomes non-responsive), you need to be sure 
 that your printers are set up correctly in the SCALE configurations. This 
 error can occur if, for example, someone changed a print device configuration 
 record to point to the wrong printer.</li>
        </ul>
