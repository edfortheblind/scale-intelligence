Personal Alerts Data Query with GraphQL

Overview

 

Personal Alerts Data Query with GraphQL allows users to define a GraphQL statement for retrieving SCALE business data as part of a Personal Alerts data query. This provides a more flexible and targeted alternative for data-retrieval scenarios that previously depended on legacy Custom SQL within Personal Alerts.

With GraphQL, users can request only the business fields needed for the use case, apply business filters, and retrieve related data in a single query. This supports reporting, monitoring, operational review, and similar data-driven use cases.

Queries are processed using the requesting user's access rights, and the returned data is limited by the applicable access and data-security rules.

 

When to Use this Feature

 

Use this feature when the business need is to:

  • Retrieve specific operational data from SCALE for a Personal Alerts data query.

  • Replace or reduce reliance on legacy Custom SQL for Personal Alerts data retrieval.

  • Filter records using business conditions such as status, carrier, quantity, date, or warehouse.

  • Retrieve related data in a single query.

  • Run a multi-step query where the result of one lookup is used to drive the next lookup.

 

GraphQL Endpoint

 

All GraphQL requests use a single endpoint:

/general/scaleapi/GraphQLApi/Query

The user role for this feature should be SCALEUSER.

 

Query Options

 

SCALE supports two main query approaches for Personal Alerts Data Query with GraphQL.

 

1. Direct Query

Use a direct query when the required information can be retrieved from a single business area, such as shipment headers, shipment details, shipping containers, receipts, locations, or inventory.

A direct query typically includes a filter to narrow the records, a field selection that identifies which business fields should be returned, and an optional limit to control result size.

If no limit is supplied, the query uses the system default maximum result limit.

 

2. Pipeline Query

Use a pipeline query when the result of one query step needs to be reused by the next step. For example, users can first identify shipments that match certain criteria and then retrieve the containers related to those shipments in the next step.

Each pipeline step identifies the step order, the method to run, any filter to apply, the fields to return, an optional limit, and whether key values should be inherited from a prior step.

If a parent step returns no results, dependent child steps are skipped instead of failing, and the pipeline can still complete successfully.

 

Filter Support

 

Filters support both field-level operators and logical operators so that users can build simple or complex business conditions.

  • eq - Equal to

  • ne - Not equal to

  • gt - Greater than

  • gte - Greater than or equal to

  • lt - Less than

  • lte - Less than or equal to

  • contains - Contains the specified text

  • startsWith - Starts with the specified text

  • endsWith - Ends with the specified text

  • in - Matches one of the listed values

  • notIn - Does not match the listed values

  • isNull - Checks whether a field is empty or not empty

.

Date and Time Keywords

 

Date-based filters support keyword expressions, making it easier to define relative dates and times in business queries.

  • TODAY - Today at midnight in local time.

  • TODAY+N or TODAY-N - A number of days after or before today.

  • NOW - Current local date and time.

  • NOW±N[d|h|m|s] - Current local date and time with an offset.

  • UTCNOW - Current UTC date and time.

  • UTCNOW±N[d|h|m|s] - Current UTC date and time with an offset.

Examples include TODAY-30, NOW-2h, and UTCNOW-1d.

 

Result Processing

 

When the Personal Alerts scheduled job runs, the system executes the GraphQL query and converts the GraphQL JSON response into flat CSV output for personal alert processing.

Pipeline responses can include an overall success indicator, the name of the last executed query, the final output data from the last step, and per-step results that show execution order, method, affected record count, status, and any error message.

Pipeline step status values are SUCCESS, FAILED, and SKIPPED.

 

Example Business Scenario

 

A customer can first identify recently created shipments for a carrier and then retrieve the associated shipping containers. This is a good fit for a pipeline query because the shipment identifiers returned in the first step can be reused automatically in the second step.

 

Best Practices

  • Use direct queries for straightforward lookups within a single business area.

  • Use pipeline queries only when one lookup depends on the results of another.

  • Select only the fields needed for the business use case.

  • Apply filters to keep result sets focused.

  • Use limits to control response volume.

  • Test broad queries carefully because very large result sets can increase processing time.

  • Verify the query before saving the personal alert configuration.

 

Additional Information

 

GraphQL provides a read-only alternative to legacy Custom SQL for Personal Alerts and supports richer entity-based query scenarios that are not possible with the standard filter builder.
