Billing Management Integration Process Summary

** Functionality **

Process Flows

 

 

Summary

Billing Management is a third-party billing application that allows customers to calculate, track, and charge for the work being performed in their warehouse. It is a stand-alone product (separate from the system) that is produced by Manhattan Associates. SCALE can integrate with Billing Management (by uploading system data to the Billing Management application) in order to facilitate a link between the inbound/outbound processing of your warehouse and the billing system of your warehouse's third-party companies.

The following are key features of the Billing Management integration functional area:

 

Prerequisites

There are the two programs that you will need to install in order to integrate with Billing Management:

  • Billing Management: This is a third-party billing application.
     
  • SQL Server Database: SCALE can only be integrated with Billing Management if you are using an SQL Server database.

 

 

Data Flow Between SCALE and Billing Management

Billing Management features APIs (application programming interfaces) that allow any system to transmit data to it (not just SCALE). It uses XML as the API transmission mechanism. Billing Management publishes various XML schemas, which describe the data elements that you can send it, and then each time you want to send data to Billing Management, the system will generate the appropriate XML-formatted data. 

 

When you run the Billing Management interface in SCALE, the system will place the appropriate data into a user-defined directory. Then, Billing Management will retrieve this data at a later time.

 

The following example outlines the flow of data for the "close load" trigger. Other triggers will function similarly:

  1. A load is confirmed. The system references the Billing Management Trigger Header records to see if any active records are associated with this event, based on Event ID.
     
  2. The system grabs the trigger header with the same Event ID as the activity (the load closing). The system retrieves the only detail without a parent value.
     
  3. The system executes the Billing Management data query record associated with this record (the Statement Field on the trigger detail record identifies which data query to use).
     
  4. The system brings back all the records defined by the data query. The system then uses the detail's you defined on the Trigger Detail Map Window to convert system data to values defined in Billing Management. This data is XML-formatted data.
     
  5. The system completes the above steps B-D for all of the remaining detail records on the trigger header. The system first processes all of the null parent record’s children, then their children, etc.
     
  6. Process history is written in the application. These history records will indicate whether or not the trigger fired and if it was successful.
     
  7. The system places the XML data into a directory, which is defined in the Billing Management System Values Window.

 

 

Billing Management Triggers

  • Trigger Processing Flow: As mentioned above, all the system business logic actually does is see if the trigger point is on, and then submit the thread to create the XML document, passing in the “key” values relevant to the operation (e.g. for receipt of a license plate it might be License Plate ID, for picking it might be the Work Unit) and the trigger identifier. Therefore, when triggers are on, the user will not see any difference in the processing flow compared to when they are off. The data is prepared automatically behind the scenes.
     
  • Adding new triggers: The user is free to add new triggers if they like; obviously adding new “run in line” triggers without adding corresponding custom processing code won’t do anything, as those require system events to check for them.  So, the main use we see for adding new triggers is related to “run manually” ones.  Note that the user would still be required to configure the proper SQL and to link up with the proper Billing Management XML schema, but the configuration could then be used to handle the mapping to the XML schema, and the base UI to allow execution of manual triggers which would then automatically show the new value.
