Researching Printing Errors

Below are some troubleshooting tips that you can use to help diagnose printing problems. If you still have questions, contact your Manhattan consultant or call the support line.

Audit Logs...

  • To perform additional research or want to review technical information, access the Audit Log Viewer Window and search for records, using criteria that meet your user ID and the date/time when you initiated the request. Always check the audit log first for errors from the following classes: PrintSupport, WordPrintProcessing, and PrintProcessing.

 

 

Document Routing Records...

  • The data does not match the criteria defined on any document routing record. For the document to print, the printing criteria defined here must be met. Review the document routing records and verify that at least one record identifies the criteria values for the data.

  • Note on Session Information and Document Routing: The system gathers "session" information when the application starts up, and stores this information for the duration that the application is open (without ever re-retrieving it). When a user goes from one client workstation to another and uses a previously open or disconnected remote desktop (RDP) session (i.e., a "stolen" RDP session), the system will NOT need to re-retrieve the session information. Therefore, the document routing process uses the "original" client device name when determining where a document should be routed. In order to prevent this (and have the document routed to the new workstation), you need to log off the RDP session when finished with a work station; or, if you disconnect from one workstation and connect to the same session from another workstation, you need to close the application and re-open it.

 

 

Printing Directory...

  • The system generates data files to two directories when printing paperwork: the "Print Data" and "Print Input" directories (which are both sub-directories of the "Printing" directory on your application server). The "Print Data" directory is used when the system writes the data files it uses for printing. Note that these files are not deleted when there is an error in printing. The "Print Input" directory is used when the system writes the control files used when printing.

  • Someone moved the Printing Directory from its install location without changing the location path in the Technical Values Window. When the system is installed, the setup tools automatically load the Printing Directory in the following location: \\WMAppServer\ILS\Printing. A record in the Technical Values Window identifies the physical location of this folder on the server. If the physical location of the Printing Directory is different than the location identified in this window, the system cannot generate documents.

 

 

Miscellaneous Hardware Errors...

  • Make sure the batch submission service is started. If no control files are being written to the "Print Input" directory, then this is most likely the cause. To confirm that no control files are being written, the user may have to stop the print engine on the application server.
     
  • Is there a .err file? If there is a ".err" file, then there will be a corresponding audit log record matching that has details as to the problem.

  • Make sure that the console is always signed on with the same profile, since printers are associated with a particular user profile. For example, printing may work fine signed on as "Administrator"; but, if you sign on to the console instead as "jdoe," the printing process will potentially break.
     
  • If there are no control files being written, then the problem is not in the print engine. Most likely, an audit log record will exist explaining why. Note that the system places these control files in the "Print Input" directory. If an error occurs when you select to print or print preview, the system usually displays an error message on the bottom of the screen. You can rectify the error and try to print/print preview again.
     
  • If no message is displayed onscreen or you need some direction in fixing the error, see your Manhattan representative.
     
  • If a hard drive error occurs during printing, the system will retry the disk operation up to ten times, and generate an audit log record for each attempt.

 

 

Print Device...

  • Make sure that the print device is identified correctly on the Print Device Window. The printer name that you define on the print device window must exactly match the printer's name that you defined via the Microsoft Windows Add Printer action.

 

 

Progistics Related...

  • If you are attempting to print a Progistics generated label, did you receive the following message: "No device is assigned to ****" (where **** is the printer's share name)? If so, the printer's network name is different than its share name and you have not communicated that difference to Progistics. See Changing the Printer's Share Name for instructions.
     
  • Is the label stock must be compatible with the printer that you're using? Be sure to verify that the stock and printer are compatible on the Print Device Window. You need to do this if the document you are printing is generated by Progistics.

 

 

PrintProcessing "Hanging" (Non-Responsive)...

  • If, after you or the system initiates a print job, and PrintProcessing seems to be "hanging" (becomes non-responsive), you need to be sure that your printers are set up correctly in the SCALE configurations. This error can occur if, for example, someone changed a print device configuration record to point to the wrong printer.
