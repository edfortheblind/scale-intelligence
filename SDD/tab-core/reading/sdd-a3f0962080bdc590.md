<a id="p003-b004"></a>
## p003\-b004 — PDF page 3, block 4

```text
 
This document is designed to outline the proposed 3PL enablement process for Supply Chain 
Architected for Logistics Execution (SCALE) at Travis Association for the Blind. The functional 
design outlined in this document is intended solely for use at the specified Travis Association for 
the Blind facility in Austin, TX. Future implementations at any other Travis Association for the 
Blind facilities will result in either change to this document or entirely new functional flows per 
facility. 
 
The objective of this document is to define the systemic and functional processes and scope 
from a Manhattan Associates’ (MA) SCALE perspective. This document serves as a reference 
throughout the 3PL enablement process for confirmation of approach and definition of tasks. It 
will also serve as a reference for Manhattan Associates’ customer support organization (CSO) 
after implementation, and potentially a reference point for any future Travis Association for the 
Blind implementations. 
 
 

```

<a id="p003-b005"></a>
## p003\-b005 — PDF page 3, block 5

```text
IMPORTANT NOTE 
 
Travis currently operates as a 3PL for a single customer (DLA). This customer has some 
contractual restrictions regarding physical access to their merchandizing. Based on the current 
contract, Travis would need to have a physical segregation (fence/wall) to keep DLA’s operation 
apart from any other operation at Travis’ warehouse. 
 
Travis is not envisioning to enable another 3PL operation in the near future, mainly because of 
the requirements of their current customer. 
 
This document will outline the requirements and recommendations to enable another 3PL.
```

## p005\-b004 — PDF page 5, block 4

```text
1. Travis will create a Company for each new 3PL customer added to their operation. 
2. The Item Master will have the Company. 
3. The SKU will be unique across companies. This is not a SCALE limitation, but having 
multiple companies with the same SKU may be a challenge for the users during work 
execution due to the use of VoCollect. 
4. The Storage Template will be defined depending on the item’s characteristics. 
5. The dimensions/weight will be maintained at the Unit of Measure level. 
6. The Treat as Loose flag will be maintained at the Unit of Measure level. 
7. Ideally Travis would need to configure new zones (locating, allocation and work) to keep 
the customers’ inventory apart from other customers. 
8. Travis may use permanent locations for items with high demand at picking locations. 
9. A new set of locating configuration (Locating rule assignment criteria, Locating rule 
assignment, Location selection and Locating rule) is required to be created per 
customer, based on the zones and companies. 
10. A new set of allocation configuration (Allocation rule assignment criteria, Allocation rule 
assignment, Allocation location selection and Allocation rule) is required to be created 
per customer, based on the zones and companies. 
11. Travis may create a new Wave flow and Wave master with specific requirements for the 
customer. Travis can also opt to use a standard Wave flow/master for all customers, as 
long as the wave flow steps are not company specific. 
12. The Item Master, Receipt Download and Shipment Download should be downloaded 
into SCALE by Travis’ middleware provider. This is a Manhattan Associates 
recommendation to keep the logic to convert the data provided by the customer into a 
format that SCALE recognizes (XML). 
13. The Item Balance Upload, Inventory Transactions Upload, Receiving Upload and 
Shipping Upload should be generated as XML files by SCALE into separate folders, one 
per customer, at the Azure Storage. From there, Travis’ middleware should pick the files 
and convert the information into the format that Travis’ customer requires. 
14. In case the customer requires the use of Lot, Travis will be able to active lot tracking at 
the Item Master. 

```

<a id="p007-b004"></a>
## p007\-b004 — PDF page 7, block 4

```text
 
Travis downloads & uploads information into SCALE using XML file-based methods of 
interfacing. 
 
This allows Travis to create records with key information for downloads, and SCALE 
reads this key information to process the download into the SCALE production tables. 
This method also allows Travis to read key information from SCALE’s upload interface 
records.  
 
Each interface touch point below can be run manually as well as through scheduled jobs 
as defined by Travis Association for the Blind. The specific schedule can depend on the 
Host System, warehouse processing times, and SCALE interface execution times. 
 
Warehouse alerts can be configured to notify Travis when a download or upload 
interface transaction has failed for any reason.
```
